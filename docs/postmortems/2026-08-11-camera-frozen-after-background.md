# 포스트모템 — 다른 앱 다녀오면 카메라가 얼어붙음

날짜: 2026-08-11 · 관련: ADR-021(카메라 복귀), ADR-013(iOS WebKit), ADR-018(편집 시트)

## 한 줄 요약

캡처 화면에서 다른 앱에 다녀오면 뷰파인더가 정지하고 **얼어붙은 낡은 프레임이 그대로 저장**됐다. 원인은 카메라 코드의 결함이 아니라 **부재** — 앱이 백그라운드에 갔다 돌아왔을 때 실행되는 코드가 저장소에 하나도 없었다.

## 증상

- 캡처 화면 → 다른 앱 → 복귀 → 뷰파인더가 **떠나기 직전 장면에서 정지**(검은 화면이 아님).
- 그 상태에서 셔터를 누르면 **지금 보는 페이지가 아니라 아까 그 장면**이 찍혀 저장됨.
- UI는 여전히 "책 페이지를 담고 셔터를 누르세요"라고 안내. 앱이 문제를 인지하지 못함.
- 앱 안에서 연속 캡처만 할 때는 멀쩡.

## 진짜 원인

`grep` 한 번으로 끝났다. 저장소 전체에서:

- `visibilitychange` / `pagehide` / `pageshow` / `freeze` / `resume` / `document.hidden` / `visibilityState` → **0건**
- `MediaStreamTrack`의 `ended` / `mute` / `unmute` 핸들러, `track.readyState`, `track.muted` → **0건**
- `document`에 등록된 이벤트 리스너 → **0개**

`app.ts`의 라우터 cleanup은 **사용자가 명시적으로 화면을 이동할 때만** 돈다. 백그라운드 전환은 라우터 입장에서 아무 이벤트도 아니다.

실패 사슬:
1. 백그라운드 → WebKit이 `<video>`를 pause시키고 카메라 트랙을 mute/ended로 만든다.
2. 복귀 → **아무 코드도 실행되지 않는다.** `video.srcObject`는 죽은 스트림을 그대로 물고, `<video>`는 마지막 디코드 프레임을 유지한다 → 정지 화면.
3. 셔터는 `video.videoWidth`도 트랙 생사도 검사하지 않고 `drawImage` → 낡은 프레임이 진짜 사진인 양 저장.

"검은 화면이 아니라 정지 화면"이라는 사용자 관찰이 결정적이었다. 스트림이 끊겼는데 화면이 남아 있다 = video가 마지막 프레임을 붙들고 있다 = 아무도 되살리지 않았다.

## 메타 원인 — 이게 진짜 교훈

ADR-013에서 **"iOS 설치형 PWA가 주 타깃 → 항상 WebKit↔Blink 차이를 의심하라"**를 확정해 놓고, 그 원칙을 **이미지 경로에만 적용했다.** 카메라 스트림에는 한 번도 적용하지 않았다.

- `src/camera/camera.ts`(58줄)는 **최초 커밋 이후 한 번도 수정된 적이 없다.**
- PRD의 멘탈 모델이 "앱 실행 → 카메라 가동, 이후 계속 켜짐"이라 **복귀 경로가 아예 존재하지 않았다.** §16 예산표의 "저장 → 카메라 복귀"조차 화면 복귀(시트 하강)를 뜻하지 스트림 재획득이 아니다.
- ADR-018은 "카메라는 시트 아래에서 계속 라이브"를 설계 목표로 삼았는데, 이때도 **스트림이 외부 요인(OS)으로 죽는 경우**는 고려 대상이 아니었다.

즉 규칙은 있었는데 적용 범위가 좁았다. **"이 원칙을 아직 적용하지 않은 곳은 어디인가"를 주기적으로 묻지 않으면 규칙은 처음 배운 자리에만 남는다.**

## 해결

`camera.ts`를 "켜고 끄는 모듈"에서 **"스트림 생사를 아는 모듈"**로 바꿨다(ADR-021).

- 생사 판정은 트랙 플래그가 아니라 **프레임이 실제로 흐르는가**로. iOS는 복귀 직후 트랙이 잠시 muted였다가 스스로 풀리기도 해서, 플래그로 분기하면 멀쩡한 스트림을 재시작하게 된다.
- 복구는 싼 것부터 2단계: `play()` → 600ms 안에 프레임이 오면 끝, 안 오면 그때만 전체 재시작.
- 셔터에 **동기** 생사 검사 — 낡은 프레임 저장 차단. 정상 경로에 비동기 대기는 추가하지 않는다(3초 루프 예산).
- 이 과정에서 잠복 버그 둘도 같이 닫혔다: `startCamera`의 스트림 누수(재진입 시 이전 스트림을 stop 없이 덮어씀), 첫-프레임 대기의 타임아웃 부재(백그라운드에서 시작하면 "카메라 준비 중…"에 영구 고착).

## 일반화할 교훈

- **결함보다 부재가 찾기 어렵다.** "무엇이 잘못 동작하나"가 아니라 **"이 상황에서 도대체 무슨 코드가 도는가"**를 물었을 때 답이 나왔다. 답이 "아무것도"면 그게 원인이다.
- **`grep`으로 부재를 증명하라.** 가설을 세우고 코드를 고치기 전에, 관련 이벤트/API가 저장소에 **0건**임을 먼저 확인하면 몇 단계를 건너뛴다.
- **원칙에는 적용 범위 점검이 따라와야 한다.** ADR-013을 세웠으면 "카메라·오디오·센서·스토리지 중 아직 안 본 곳"을 그때 목록으로 남겼어야 했다.
- **정지 화면 ≠ 검은 화면.** 사용자에게 "어떻게 보이나요"를 정확히 물으면 실패 지점이 좁혀진다. 검은 화면이면 srcObject가 끊긴 것, 정지 화면이면 요소가 마지막 프레임을 붙든 것 — 원인이 다르다.
- **재현할 수 없는 환경이라도 로직은 테스트할 수 있다.** iOS 백그라운드 전환은 헤드리스로 못 만들지만, 트랙을 강제로 stop하고 `visibilitychange`를 쏘면 **같은 상태**가 된다. 단, 테스트가 헛돌지 않게 **"정말 죽어 있었는지"를 먼저 단언**할 것.
- **센서를 읽기 전에 살아 있는지 확인하라.** 카메라·마이크·위치는 앱이 모르는 사이 OS가 뺏어간다. 마지막으로 성공한 값이 아직 유효하다고 가정하지 말 것.
